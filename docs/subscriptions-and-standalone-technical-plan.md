## 1. الهدف والقرار المعماري

دعم منتج واحد بمستودع وشيفرة ومخطط قاعدة بيانات موحّد، مع طريقتين للتسليم:

| الجانب | SaaS | Standalone — نسخة مستقلة |
|---|---|---|
| الاستضافة | في استضافة مالك فيزانو | خادم الشركة أو استضافتها الخاصة |
| البيانات | شركات معزولة داخل النشر | قاعدة بيانات وملفات خاصة بالعميل |
| الإدارة | إدارة منصة مركزية + مالك لكل شركة | إدارة تثبيت محلية + مالك الشركة |
| الحق التجاري | اشتراك بخطة ومدة | رخصة شراء دائمة أو محددة المدة |
| التحديثات والنسخ الاحتياطي | مسؤولية مشغل المنصة | مسؤولية الشركة أو خدمة صيانة متعاقد عليها |
| الاتصال بفيزانو | تشغيل الخدمة السحابية | لا اتصال إلزامي للتشغيل اليومي؛ تفعيل وتحديث يدويان متاحان |

«مستقلة» تعني نسخة قابلة للتثبيت لدى العميل، ولا تستلزم تحويل النظام إلى خدمات موزعة. يبقى Django تطبيقًا واحدًا مع Next.js المصدّر وPostgreSQL للإنتاج. تبقى أدوات Celery والجدولة خدمات تشغيل مساندة عند الحاجة.

طلب المستخدم الحالي يوسّع نص الاستضافة المركزية الموجود في `PROJECT_RULES.md`. أول خطوة تنفيذية هي تحديث فقرة الاستضافة لتسمح بالنسخة المستقلة، مع إبقاء قواعد عزل الشركات والتدقيق والمدفوعات اليدوية وعدم استخدام Docker. هذه الوثيقة وحدها لا تعدّل قواعد التشغيل.

## 2. ما يجب الحفاظ عليه

- لا نسخ منفصلة من الشيفرة لعملاء مختلفين، ولا حذف `company_id` في النسخة المستقلة.
- لا حذف مستخدمين أو أقسام أو معاملات عند انتهاء اشتراك أو تغيير خطة.
- لا استخدام `User.is_active` أو `Company.is_active` لتعليق الاشتراك؛ لهما معنى إداري قائم.
- لا خلط فواتير اشتراك فيزانو بفواتير الشركة لعملائها أو دفتر ديونها.
- لا تحويل بيانات الشركة أو أنماط واجهتها عند تغيير نمط النشر.
- لا إتاحة شراء باقة أو تعديل رخصة لمجرد امتلاك صلاحية المدير المالي.
- لا اشتراط الوصول إلى خادم ترخيص خارجي لتشغيل النسخة المستقلة الدائمة.
- الحفاظ على واجهات الأعمال الحالية، وإضافة واجهات الاشتراك والترخيص بجانبها.

## 3. فصل أربع سياسات مستقلة

1. **نمط النشر:** إعداد خادم `VEZANO_DEPLOYMENT_MODE=saas|standalone`. لا يتغير من شاشة الشركة.
2. **الحقوق التجارية:** الوحدات والحدود التي تمنحها الخطة أو الرخصة.
3. **وضع العمل:** وضع الشركة أو المتجر، باختيار المالك وفق المنطق الحالي.
4. **صلاحيات المستخدم:** الدور والاستثناءات والفرع ونطاق الشركة.

السماح بالعملية يتطلب تحقق السياسات الأربع المتعلقة بها: حق الشركة في الوحدة + حق المستخدم في العملية + السماح حسب وضع العمل + نطاق الشركة والفرع. الاشتراك لا يمنح صلاحيات موظف، والاستثناء في وضع المتجر لا يفتح وحدة غير مرخّصة.

## 4. وحدات الشيفرة المقترحة

| الموضع | المسؤولية |
|---|---|
| `backend/subscriptions/` | الخطط والإصدارات والاشتراكات والفواتير والتحصيل اليدوي |
| `backend/licensing/` | قراءة الرخص الموقّعة والتحقق منها وتفعيلها محليًا |
| `backend/core/entitlements.py` | واجهة موحدة لحساب الحقوق دون معرفة مصدرها |
| `backend/core/permissions.py` | دمج الحقوق مع فحص DRF بعد المصادقة |
| `backend/config/deployment.py` | قراءة نمط النشر والتحقق من إعداداته |
| `frontend/.../subscription/` | واجهة مالك الشركة للاشتراك |
| `frontend/.../platform-subscriptions/` | واجهة مشغل SaaS |
| `frontend/.../license/` | واجهة رخصة التثبيت المستقل |
| `deploy/standalone/` | قوالب تشغيل أصلية ودليل تثبيت وترقية واستعادة |

تعمل خدمة الحقوق بموفر SaaS أو موفر رخصة محلية. التسجيل والتحصيل وإصدار الرخص لا يدخل في خدمات المبيعات والرواتب والمخزون.

## 5. نموذج البيانات

| النموذج | الحقول/القواعد الأساسية |
|---|---|
| `Plan` | رمز ثابت واسم وحالة إتاحة للبيع؛ لا تُحذف خطة مستخدمة |
| `PlanVersion` | إصدار غير قابل للتعديل بعد الاستخدام، العملة والسعر والدورة والوحدات وحدود الاستخدام |
| `Subscription` | شركة واحدة، إصدار الخطة، الحالة، بداية ونهاية الفترة، نهاية التجربة والسماح، الإلغاء المجدول، نسخة التزامن |
| `SubscriptionEvent` | سجل أحداث غير قابل للحذف: تفعيل وتجديد وتغيير خطة وتعليق واستعادة، الفاعل والسبب ومفتاح منع التكرار |
| `SubscriptionInvoice` | مستند مستقل مرقّم، الفترة والمبلغ والعملة وتاريخ الاستحقاق ولقطة بنود الفاتورة؛ لا تعديل للمستند المُصدر |
| `SubscriptionPayment` | تسجيل يدوي وإثبات ومرجع ومراجعة بشرية وحالة؛ التصحيح بسجل مقابل |
| `PaymentAllocation` | توزيع دفعة على فواتير الاشتراك، مع منع توزيع أكثر من قيمتها |
| `EntitlementOverride` | استثناء تجاري محدد المدة والنطاق والسبب والفاعل؛ يختلف عن استثناء وضع المتجر |
| `Installation` | معرف تثبيت ثابت ونمط النشر وإصدار التطبيق وهوية الجهة المالكة؛ ليس FK رقميًا من SaaS |
| `LicenseActivation` | الرخصة الموقعة ومعرفها ومصدرها ونوعها وحقوقها وتواريخها ومعرف مفتاح التوقيع |

كل بيانات SaaS المالية مرتبطة بالشركة المستفيدة، وتبقى متاحة لإدارة المنصة المختصة فقط. تعريفات الخطط مفهرس عالمي مقصود. لا تظهر إثباتات السداد ضمن ملفات الشركة العامة.

تظل بيانات `Company` التشغيلية كما هي. الربط بالاشتراك إضافي، ولا يُشترط وجود اشتراك مباشرة على جميع الشركات في أول ترحيل.

## 6. دورة الاشتراك

| الحالة | الأثر |
|---|---|
| `trialing` | تشغيل الوحدات والحدود الممنوحة للتجربة حتى تاريخها |
| `active` | تشغيل الحقوق المتعاقد عليها |
| `grace` | استمرار مؤقت مع تنبيه للمالك عن التجديد |
| `read_only` | إيقاف عمليات الأعمال الجديدة، مع قراءة البيانات وتصديرها ضمن صلاحيات كل مستخدم |
| `suspended` | تعليق إداري مستقل عن انتهاء المدة؛ يبقى مسار المالك للاشتراك والدعم متاحًا حسب سبب التعليق |
| `cancelled` | انتهاء العلاقة التجارية؛ الاحتفاظ بالبيانات وفق سياسة معلنة، دون حذف تلقائي في هذه المرحلة |

اقتراح البداية: تجربة 14 يومًا وسماح 7 أيام، قابلان للضبط وليسا افتراضًا ثابتًا في الشيفرة. الإلغاء أثناء فترة مدفوعة يُجدول لنهايتها. التجديد قبل الانتهاء يمدد من نهاية الفترة المدفوعة، وبعد الانتهاء يبدأ من تاريخ إعادة التفعيل ما لم يُسجل اتفاق مختلف صراحة.

تُحسب الحالة الفعلية وقت الطلب من التواريخ والأحداث، فلا يعتمد المنع على نجاح مهمة يومية. تستخدم المهام المجدولة لإرسال التنبيهات وتحديث العرض، مع منع تكرار الإشعار.

الترقية في المرحلة الأولى تُجدول للدورة التالية؛ الترقية الفورية تتطلب فاتورة تعديل معتمدة يدويًا. لا حساب تلقائي لفروقات أسعار جزئية قبل تحديد السياسة التجارية.

تخفيض الخطة فوق الاستخدام الحالي لا يحذف بيانات ولا يعطل موظفين اعتباطيًا: يُمنع إنشاء موارد إضافية، وتظهر للمالك الموارد الزائدة، ويؤجّل التغيير عند وجود تعارض مع الوحدة أو الموظفين اللازمين للتشغيل حتى يحدد المالك المعالجة.

## 7. تعريف الحقوق وحدود الاستخدام

واجهة مقترحة: `resolve_entitlements(company, installation)` تعيد الوحدات والحدود وحالة الكتابة ومصدر القرار ونسخة الحقوق وتاريخ انتهاء صلاحية القرار.

الحدود الأولية: المستخدمون النشطون، الفروع النشطة، المستودعات النشطة، وحدات HR/الرواتب/CRM، وحجم الملفات. يتم تعريف معنى «نشط» بدقة: تعليق الوصول بسبب وضع المتجر لا يقلل عدد حسابات الاشتراك؛ الأرشفة الإدارية فقط تؤثر في العد المحدد للباقة. لا نضع حدًا على السجلات المالية التاريخية.

فحص الحدود يتم في الخادم قبل الإنشاء داخل معاملة، مع قفل عداد/سجل الشركة حتى لا ينجح طلبان متزامنان في تجاوز آخر مقعد. تُرفض العمليات المركبة بالكامل عند عدم كفاية الحق، ولا يُحفظ نصف مستند.

عند إغلاق وحدة مرخّصة تُتاح قراءة تاريخها وتصديره لمن كان يملك صلاحية القراءة. يجب تعريف تبعيات الوحدات؛ مثلًا POS يحتاج مخزونًا وعملاء وتسوية مدفوعات، والرواتب تحتاج موظفين وسلفًا واستقطاعات. لا تُباع تركيبة تمنع إكمال عملية أساسية.

## 8. تطبيق السياسة على API والمزامنة

- طبقة DRF بعد حل هوية المستخدم، وخدمة مشتركة تستدعيها العمليات الخلفية و`sync/services.py` وأوامر الإدارة التي تنشئ معاملات أعمال.
- خريطة صريحة لكل إجراء إلى الوحدة ونوع العملية؛ لا يكفي منع كل POST لأن تسجيل الدخول أو طلب تجديد قد يستخدم POST.
- أخطاء مستقرة مثل `subscription_read_only` و`plan_limit_reached` و`license_invalid`، مع ترجمة واضحة بالواجهة.
- للموظف رسالة مختصرة «تواصل مع مالك الشركة». تفاصيل الأسعار والتحصيل للمالك فقط.
- الرد المتكرر لعملية سبق نجاحها يرجع المستند السابق دون إنشاء كتابة جديدة، حتى لو انتهى الاشتراك لاحقًا، بعد التحقق من الهوية والنطاق.
- عملية offline لم تُنفذ بالخادم تخضع للحالة الحالية. لا يُوثق تاريخ الجهاز كدليل لاستحقاق قديم. تبقى العملية في الطابور عند الرفض، مع إعادة المحاولة بعد التجديد وعدم حذف بياناتها.
- انتهاء ذاكرة الحقوق المؤقتة لا يتحول إلى سماح مفتوح؛ يُستخدم آخر قرار صالح لمدة محددة، ثم قراءة فقط عند تعذر الحسم. المالك يستطيع الوصول لمسار التسوية والتجديد.
- لا تعطل سياسة الاشتراك فحوص الصحة أو الخروج أو النسخ الاحتياطي أو استعادة الوصول؛ تحدد القائمة لكل نمط نشر، ولا تفتح وصولًا عامًا للبيانات.

## 9. الشاشات والصلاحيات

### إدارة منصة SaaS

واجهة مخصصة لمشغل المنصة: الخطط، الشركات واشتراكاتها، الفواتير المستحقة، مراجعة المدفوعات اليدوية، التجديد والتعليق والاستثناءات وسجل الأحداث. لا تمنح هذه الواجهة الاطلاع على معاملات الشركة التشغيلية تلقائيًا؛ تُفصل صلاحية إدارة الاشتراك عن دور الدعم أو superuser.

### مالك الشركة

صفحة «اشتراك الشركة»: الخطة والحالة والتواريخ والاستخدام والفواتير وتعليمات التحويل اليدوي ورفع الإثبات وطلب التغيير. الرفع لا يفعّل الاشتراك وحده؛ المراجعة للمشغل المخول. يمكن لاحقًا تفويض موظف محدد دون توسيع صلاحيات جميع المديرين الماليين.

### النسخة المستقلة

صفحة «رخصة النظام»: اسم الجهة، معرف التثبيت، الحقوق، إصدار التطبيق، صلاحية الاستخدام والصيانة كل على حدة، استيراد رخصة وتجديدها، وخيارات النسخ الاحتياطي والتحديث. تختفي واجهات بيع اشتراكات SaaS وطلبات المنصة العامة من هذه النسخة.

## 10. الترخيص المستقل والاستقلال الفعلي

الرخصة ملف ذو توقيع غير متماثل، يحتوي `license_id` و`installation_id` والجهة والوحدات والحدود ونوع الرخصة والتواريخ ونطاق الإصدارات ومُعرف مفتاح التوقيع. يوجد المفتاح العام فقط لدى العميل؛ مفتاح الإصدار الخاص يبقى لدى بائع فيزانو خارج مستودع التوزيع.

- **دائمة:** حق تشغيل دائم للإصدارات المشمولة. انتهاء الصيانة يوقف استحقاق تحديثات جديدة والدعم وفق العقد، ولا يوقف المبيعات أو الرواتب.
- **محددة المدة:** تاريخ استعمال ونهاية سماح معلنان؛ بعدهما قراءة وتصدير وتجديد وفق السياسة.
- تفعيل دون إنترنت: توليد طلب تفعيل محلي، توقيعه لدى البائع، واستيراد ملف الرخصة لدى الشركة.
- معرف التثبيت محفوظ ومُضمّن في النسخ الاحتياطية. تغيير الخادم له مسار إعادة استضافة، دون ربط هش بعنوان IP أو بطاقة شبكة.
- لا مزامنة تلقائية لبيانات الموظفين والعملاء والمعاملات إلى البائع، ولا حساب دعم خلفي مخفي. أي وصول دعم تمنحه الشركة صراحة بمدة محددة ويُسجل.
- من يملك الخادم والشيفرة يمكنه محاولة تعديل آلية الترخيص؛ التوقيع يمنع تزوير ملف أصلي، ولا يحقق حماية مطلقة ضد مالك الجهاز. لا تُستخدم آليات تمس بيانات العميل أو تعطل النسخة الدائمة عند انقطاع الإنترنت.

النطاق الأول للتثبيت: شركة واحدة وفروعها. يبقى عزل `company_id` فعالًا، وتُختبر إمكانية إتاحة عدة كيانات قانونية برخصة لاحقة، دون تحويل مدير التثبيت المحلي إلى مدير SaaS مركزي.

## 11. حزمة التوزيع والتحديث

هدف الدعم الأول خادم Linux محلي أو VPS، مع PostgreSQL، وملفات/وسائط محلية أو تخزين تختاره الشركة، وخادم ويب TLS، وتشغيل Django وCelery والجدولة كخدمات أصلية. لا يعتمد التثبيت على Render. لا تُدرج أسرار التطوير أو قاعدة البيانات الحالية أو بيئة Python المحلية في الحزمة.

كل إصدار يتضمن: رقم إصدار، قائمة تبعيات مثبتة، ملفات frontend مبنية، migrations، ملف إعداد نموذجي، أوامر التثبيت والفحص، دليل النسخ والاستعادة والترقية، سجل تغييرات، وبصمات تحقق وتوقيع للحزمة. تُراجع شروط إعادة توزيع التبعيات قبل أول بيع.

التثبيت الأول ينشئ الشركة والمالك محليًا دون كلمة مرور افتراضية مشتركة، ويتحقق من الرخصة والإعدادات. صلاحيات إدارة الخادم منفصلة عن صلاحيات العمل. لا تفتح شاشة التهيئة مجددًا بعد الإعداد.

التحديث عملية يختارها مدير التثبيت: فحص إصدار وقاعدة، نسخة احتياطية مؤكدة، وضع صيانة قصير إن لزم، تطبيق الترحيلات، اختبارات صحة، ثم إعادة الخدمة. يسمح المسار غير المتصل باستيراد الحزمة يدويًا. الرجوع للشيفرة فقط لا يكفي بعد migration غير متوافق؛ يُستخدم الإصدار السابق مع استعادة نسخة متوافقة وفق إجراء مدروس.

## 12. النسخ الاحتياطي ونقل SaaS إلى مستقل

الموجود في `ops/services.py` يصدّر مجموعة محدودة ويعيد البيانات الأساسية فقط؛ لا يصلح أساسًا للادعاء بتعافٍ كامل. تعد تجربة استعادة قاعدة البيانات والوسائط شرطًا لتسليم النسخة المستقلة.

يحتاج نقل شركة من SaaS إلى مستقل إلى أداة تصدير/استيراد خاصة بالشركة تشمل جميع العلاقات والوثائق والملفات والسجلات والتعدادات، مع قائمة سماح للنماذج. لا تُنقل قاعدة SaaS كاملة ولا بيانات الشركات الأخرى ولا حسابات إدارة المنصة أو أسرارها أو جلساتها أو رموز دخولها.

إجراء النقل: تصدير تجريبي → استيراد مع خريطة معرفات → مقارنة أعداد السجلات والأرصدة والمخزون والرواتب وعينات الملفات → نافذة إيقاف كتابة ومزامنة معلنة → تصدير نهائي → اختبارات قبول → توجيه المستخدمين → أرشفة المصدر حسب الاتفاق. تُعالج طوابير offline القديمة قبل القطع أو تُعزل وتُرحّل بخريطة معتمدة لمنع التكرار.

تظل التجربة التجريبية ونسخة المصدر قابلتين للمراجعة خلال فترة قبول محددة. النقل العكسي إلى SaaS مرحلة لاحقة، ولا يُقدم كزر تغيير وضع النشر.

## 13. إدخال الميزة دون كسر النظام

1. ترحيلات إضافية فقط في البداية، دون إزالة حقول أو إعادة تفسير الحالات الحالية.
2. إعداد تطبيق سياسة الاشتراك `disabled|observe|enforce` يتحكم فيه الخادم، مع منع تبديله من API الشركة.
3. ترحيل الشركات الحالية إلى حق محفوظ `legacy` بنفس الوحدات والحدود العملية السابقة؛ لا بدء تجربة قصيرة لها تلقائيًا ولا تعطيل شركة عند غياب سجل جديد.
4. في `observe` تُسجل القرارات المحتملة دون منع العمليات. تُقارن تدفقات POS والرواتب والمخزون والتقارير قبل وبعد التغيير.
5. تجربة على شركات مخصصة ومحددة، ثم تفعيل تدريجي. الشركات الجديدة بعد الإطلاق تحتاج خطة أو تجربة صريحة، ولا يرث غياب السجل سماح legacy.
6. رفع التطبيق إلى `enforce` بعد اعتماد مصفوفة العمليات ورسائل الواجهة واختبارات العزل. خيار التراجع يعطل فحص الحقوق الجديدة فقط ولا يمس RBAC أو عزل الشركات.
7. قرار الرجوع لا يحذف أحداث التجديد أو المدفوعات أو الحقوق الممنوحة. لا تحويل عشوائي بين SaaS ومستقل بإعداد بيئة فوق قاعدة بيانات مستخدمة.

## 14. مراحل التنفيذ والتسليم

الأرقام تقديرات تخطيطية أولية لمهندس متفرغ مع مراجعة واختبار، وليست التزامًا زمنيًا. لا تُجمع كوعود قبل تفصيل القصص.

| المرحلة | الناتج | معيار القبول | التقدير |
|---|---|---|---|
| 0 | تحديث القواعد، ADR للنشر، مصفوفة الأدوار والعمليات والتبعيات | توثيق مصدر كل قرار وصول وعدم خلط النشر بوضع المتجر | 2–3 أيام |
| 1 | نماذج الخطط والإصدارات والاشتراكات والأحداث، وترحيل legacy | لا اختلاف وظيفي للشركات الحالية، rollback تجريبي | 3–5 أيام |
| 2 | خدمة الحقوق ووضع observe والتكامل مع API وoffline والمهام | كل عمليات الكتابة المهمة مغطاة ولا منفذ يتجاوز السياسة | 4–6 أيام |
| 3 | لوحة المنصة والمالك والفواتير والتحصيل اليدوي والتجديد | دورة تجربة وتجديد وانتهاء وإعادة تفعيل كاملة | 5–7 أيام |
| 4 | رخص مستقلة موقعة وتهيئة محلية وواجهات حسب النشر | تشغيل دائم دون الاتصال بالبائع وفصل الصيانة عن الرخصة | 4–6 أيام |
| 5 | حزمة تثبيت وترقية ونسخ واستعادة | تثبيت على خادم نظيف واستعادة موثقة | 4–6 أيام |
| 6 | نقل شركة من SaaS إلى مستقل | تطابق الأرصدة والسجلات وعدم تسريب أي شركة أخرى | 4–7 أيام |
| 7 | اختبارات إنتاج تجريبي وإطلاق تدريجي ودليل تسليم | نجاح مصفوفة القبول وتوثيق الحدود المتبقية | 3–5 أيام |

النسخة الأولى التجارية لـ SaaS تُسلّم بعد المرحلة 3 واختبارات إطلاقها. النسخة المستقلة لا تُباع قبل اجتياز المرحلة 5. نقل العملاء القائمين يحتاج المرحلة 6.

## 15. مصفوفة اختبارات القبول

- النظام الحالي: حزمة انحدار كاملة، مع مقارنة بيانات مرجعية للفواتير والمخزون والرواتب والديون دون تعديل الأرصدة القديمة.
- SaaS: تجربة وتنبيه وانتهاء وسماح وتجديد مبكر ومتأخر وإلغاء وجدولة تغيير خطة.
- صلاحيات: المالك والمالية وHR والموظف ومشغل الاشتراك ومدير التثبيت؛ منع تصعيد الدور وتسريب فواتير اشتراك شركة أخرى.
- الحدود: طلبان متزامنان لآخر مقعد أو فرع، والتخفيض عند تجاوز الحد، وتبعيات الوحدات.
- المال: إعادة تأكيد دفعة مرتين، معالجة طلبين متزامنين، حدود توزيع الدفعات، مراجعة بشرية، وتصحيح دون محو سجل.
- offline: إعادة عملية ناجحة بعد الانتهاء، عملية لم تُرسل سابقًا، تبديل المستخدم أو الشركة، وتكرار إرسال الدفعة بعد التجديد.
- الوقت: حدود منتصف الليل واختلاف المناطق الزمنية وتأخر المهمة المجدولة وتوقف cache؛ مقارنة التواريخ بمرجع خادم متسق.
- المستقل: رخصة صحيحة ومعدلة وخاطئة التوقيع أو التثبيت، تشغيل بلا إنترنت، انتهاء صيانة دائمة، إعادة استضافة، وغياب واجهات SaaS.
- النشر: PostgreSQL فعلي للتزامن، تثبيت نظيف، ترقية من الإصدار السابق، نسخة احتياطية واستعادة كاملة، وفشل آمن وسط الترحيل.
- الواجهة: العربية وRTL والجوال ورسائل أسباب المنع وعدم اختفاء البيانات السابقة.

## 16. القرارات التجارية قبل الإطلاق

لا تمنع هذه القرارات بناء الأساس التقني، لكن تُحسم قبل بيع الخدمة:

- أسعار الباقات وعملاتها وعدد المستخدمين والفروع والوحدات في كل باقة.
- مدة التجربة والسماح وسياسة الإلغاء والاسترداد والاحتفاظ بالبيانات.
- تسعير النسخة المستقلة: حق دائم أو مؤقت، مدة الصيانة، وطريقة استحقاق تحديثات الإصدارات.
- الجهة التي تدير الخادم والنسخ الاحتياطي لدى العميل ومستوى الدعم ونقل الخادم.
- نطاق عدد الشركات القانونية في رخصة مستقلة؛ الافتراض الأول شركة وفروعها.

الدفع يظل يدويًا في الخطة الأولى وفق قواعد المشروع. أي بوابة دفع مستقبلية لاشتراكات المنصة تتطلب نطاق عمل مستقلًا ولا تتصل بتسجيل مدفوعات عملاء الشركات.

## 17. تعريف الإنجاز

يمكن لشركة استخدام SaaS بخطة وتجديد واضحين، ويمكن تسليم نفس إصدار فيزانو لشركة تديره بقاعدة وملفات وحسابات محلية مستقلة. انتهاء الاشتراك أو الصيانة لا يحذف بيانات، وكل تغيير تجاري قابل للتدقيق، ولا يتغير منطق الأعمال أو صلاحيات الأقسام عند إدخال الميزة. يُسلّم سجل اختبارات لكل مرحلة ودليل تشغيل واستعادة، مع تحديد ما لم يُختبر دون ادعاء ضمان مطلق بعدم الأعطال.
