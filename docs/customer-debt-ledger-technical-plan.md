# الخطة التقنية لتنفيذ دفتر ديون العملاء

- المشروع: ERP Platform
- الحالة: خطة مقترحة للتنفيذ؛ ليست توثيقًا لميزة منفذة
- التاريخ: 2026-09-11
- المرجع البرمجي وقت إعداد الخطة: `91b850b`
- النطاق: ديون العملاء داخل وحدة المبيعات، مع واجهة مبسطة لوضع المتجر

## 1. الهدف

بناء دفتر موحد يوضح ما على العميل وما له، ويربط كل مبلغ بمستنده الأصلي، ويتيح تسجيل السداد وطباعة كشف الحساب. مصدر الرصيد هو الحركات المالية المسجلة، دون حقل رصيد مستقل قابل للتعديل أو نسخ الفواتير إلى جدول ديون موازٍ.

يبدأ التسليم بديون الفواتير الحالية، ثم تسجيل السداد وتوزيعه، ثم الديون السابقة لاستخدام النظام والتصحيحات.

## 2. الأساس الموجود في المشروع

| المكوّن الحالي | الاستفادة منه | الفجوة المطلوبة |
| --- | --- | --- |
| `Customer` و`Invoice` و`Payment` في `backend/sales/models.py` | العملاء والفواتير والمدفوعات | كل دفعة مرتبطة بفاتورة واحدة؛ تجميع سداد لعدة مستحقات يحتاج تصميمًا إضافيًا |
| `Invoice.amount_due()` | المتبقي بعد المدفوعات والإشعارات الدائنة | توحيد استعماله وتعريفاته في استعلامات الدفتر |
| `/api/customers/{id}/records/` | سجل العميل والأحداث العامة | ليس كشفًا ماليًا برصيد متحرك؛ يتضمن عروض أسعار وطلبات غير منشئة للدين |
| الإشعارات الدائنة والمرتجعات | تخفيض المستحقات وفق المستندات المعتمدة | منع خصم المرتجع والإشعار الدائن مرتين |
| المزامنة و`client_uuid` | إعادة المحاولة دون تكرار العملية | إضافة عقد واضح لسند السداد وتعارضاته |
| الصلاحيات وسجل التدقيق والطباعة | إعادة استخدام البنية القائمة | تغطية العمليات والنماذج الجديدة |

## 3. النطاق

### ضمن التنفيذ

- قائمة العملاء المدينين والبحث بالاسم والهاتف.
- إجماليات المستحقات والمتأخرات والأرصدة الدائنة.
- كشف حساب مالي بفترة ورصيد بداية ونهاية.
- تسجيل سداد نقدي أو تحويل بنكي يدوي.
- توزيع السداد على مستحقات محددة أو على الأقدم بعد معاينة.
- سند سداد وكشف حساب قابلان للطباعة بالعربية والإنجليزية.
- ربط البيع الآجل بعميل محدد.
- ديون افتتاحية موثقة وتصحيحات بحركات مقابلة.
- المزامنة، الصلاحيات، عزل الشركات والفروع، وسجل التدقيق.

### مؤجل إلى طلب مستقل

- دفتر مستحقات الموردين.
- تذكيرات واتساب أو رسائل تلقائية.
- الفوائد والغرامات.
- بوابات الدفع.
- استيراد دفاتر قديمة من ملفات.
- دفتر أستاذ عام أو محاسبة متعددة العملات.

## 4. قواعد الحساب

1. استخدام `Decimal` في الخادم وإرجاع المبالغ كنصوص عشرية إلى الواجهة.
2. فصل إجمالي المستحقات عن الرصيد الدائن؛ لا مقاصة تلقائية بينهما دون عملية موثقة.
3. عدم احتساب عروض الأسعار وطلبات البيع كدين.
4. تخفيض الدين بالإشعار الدائن مرة واحدة دون تخفيض إضافي للمرتجع نفسه.
5. فصل تاريخ الحركة المالي عن وقت تسجيلها الفعلي.
6. منع البيع الآجل لعميل مجهول. تعرض الفواتير القديمة غير المرتبطة بعميل في تقرير استثناءات دون إسناد تلقائي.
7. الدين المتأخر هو مستحق موجب تجاوز تاريخ استحقاق محددًا.
8. الحركة المالية المعتمدة لا تعدّل أو تحذف؛ التصحيح بحركة مقابلة مرتبطة بالأصل.
9. يبدأ كشف الفترة برصيد الحركات السابقة لها، ويعرض رصيدًا متحركًا بترتيب ثابت عند تساوي التواريخ.

المعادلة التشغيلية: المديونية الافتتاحية + المبيعات الآجلة − السداد − التخفيضات المعتمدة، مع عرض أي رصيد دائن بصورة مستقلة.

## 5. البنية البرمجية المقترحة

يبقى التنفيذ داخل تطبيق Django الحالي `sales` دون إنشاء خدمة مستقلة.

| المكوّن المقترح | المسؤولية |
| --- | --- |
| `backend/sales/debt_queries.py` | قوائم المدينين والإجماليات وفلاتر الاستحقاق |
| `backend/sales/debt_services.py` | تسجيل السداد وتوزيعه والتحقق من التزامن |
| `backend/sales/debt_statements.py` | بناء كشف الحساب والرصيد المتحرك |
| serializers وviews مخصصة | التحقق من المدخلات والصلاحيات وعرض النتائج |
| `frontend/app/(app)/debts/page.jsx` | شاشة دفتر الديون |
| مكوّنات واجهة فرعية | قائمة المدينين، كشف العميل، معاينة السداد وتأكيده |

تستخدم الشاشة والطباعة والتصدير نفس تعريفات الحساب. تستخدم استعلامات مجمعة وترقيم صفحات، مع تجنب استعلام منفصل لكل عميل أو فاتورة. يحدد هدف الأداء الرقمي بعد قياس بيانات اختبار ممثلة للحجم المتوقع.

## 6. تصميم البيانات المقترح

ديون الفواتير تستخدم النماذج القائمة. النماذج التالية إضافات مقترحة تحتاج مراجعة مخطط البيانات قبل التنفيذ:

| النموذج | الغرض والحقول الرئيسية |
| --- | --- |
| `DebtReceipt` | سند سداد واحد: الشركة، العميل، الفرع، المبلغ، الطريقة، البيانات البنكية عند الحاجة، المسجل، التاريخ، `client_uuid` |
| `DebtAllocation` | تخصيص جزء من السند لفاتورة أو دين افتتاحي، ورابط إلى `Payment` المنشأ للفاتورة |
| `OpeningDebt` | دين سابق: الشركة، العميل، الفرع، المبلغ، تاريخ الدين، الاستحقاق الاختياري، المرجع، السبب، المسجل |
| `OpeningDebtCorrection` | تصحيح موثق مرتبط بالدين الافتتاحي، بمبلغ واتجاه وسبب |

عند سداد فاتورة، ينشئ النظام `Payment` المعتاد ويربطه بالتوزيع. يحتسب المبلغ مرة واحدة؛ `DebtReceipt` يجمع العملية ولا يمثل خصمًا إضافيًا فوق مدفوعاته التابعة.

### القيود

- مجموع التوزيعات يساوي مبلغ السند.
- لكل توزيع مستحق واحد فقط: فاتورة أو دين افتتاحي.
- جميع العلاقات تتبع الشركة والعميل الصحيحين وتلتزم بنطاق الفرع.
- المبالغ موجبة؛ التصحيح له اتجاه أو نوع صريح.
- منع تعديل الحركات المعتمدة وحذفها.
- معرّف إعادة المحاولة فريد ضمن نطاق محدد وثابت.
- إضافة قيود قاعدة بيانات للقيود القابلة للتمثيل، والتحقق الذري داخل الخدمة للقيود العابرة لعدة صفوف.

### قرارات يجب تثبيتها قبل الترحيلات

- معالجة وإلغاء أو عكس سند سداد خاطئ دون تغيير `Payment` المعتمد في مكانه.
- سياسة استخدام الرصيد الدائن أو رده للعميل؛ لا تسوية ضمنية.
- تاريخ القطع للديون الافتتاحية، ومنع ازدواجها مع فواتير سابقة مسجلة بالفعل.
- سياسة السداد الزائد: رفضه افتراضيًا في النسخة الأساسية ما لم تعتمد آلية مستقلة للدفعات المقدمة.
- تكامل السداد مع الصندوق والبنوك والتقارير دون ازدواج في الاحتساب.

لا تبدأ الترحيلات قبل اعتماد هذه القرارات والتحقق من النسخ الاحتياطي والاستعادة. أي تغيير مطلوب في نموذج قائم يوثق صراحة قبل تنفيذه.

## 7. واجهات API المقترحة

| الطريقة والمسار | الوظيفة |
| --- | --- |
| `GET /api/debts/customers/` | قائمة العملاء وأرصدتهم مع البحث والتصفية والترقيم |
| `GET /api/debts/summary/` | المستحقات والمتأخرات والأرصدة الدائنة |
| `GET /api/customers/{id}/debt-statement/` | كشف مالي بفترة ورصيد افتتاح وختام |
| `POST /api/debt-receipts/preview/` | معاينة توزيع السداد دون حفظ |
| `POST /api/debt-receipts/` | اعتماد السداد والتوزيعات |
| `GET /api/debt-receipts/{id}/document/` | سند قابل للطباعة |
| `POST /api/opening-debts/` | تسجيل دين افتتاحي |
| `POST /api/opening-debts/{id}/corrections/` | تسجيل تصحيح موثق |

المعاينة لا تحجز الرصيد. يعيد الخادم التحقق عند الاعتماد؛ إذا تغيرت المستحقات يعيد تعارضًا واضحًا ويطلب تحديث المعاينة. تثبت أسماء الحقول ورموز الأخطاء وعقد الترقيم والتصفية قبل تنفيذ الواجهة.

حقول كشف الحساب الأساسية: التاريخ، نوع الحركة، المرجع، الزيادة، التخفيض، والرصيد بعد الحركة. يجب أن تتفق حدود الفترة وترتيب الحركات في الشاشة والطباعة والتصدير.

## 8. التزامن ومنع التكرار

مسار تسجيل السداد:

1. بدء `transaction.atomic()`.
2. التحقق من الشركة والعميل والفرع والصلاحيات.
3. فحص مفتاح إعادة المحاولة ومطابقة محتوى الطلب.
4. قفل المستحقات باستخدام `select_for_update()` بترتيب ثابت.
5. إعادة حساب المتبقي والتحقق من التوزيع.
6. إنشاء السند والتوزيعات والمدفوعات وتسجيل التدقيق.
7. نجاح الحفظ كاملًا أو التراجع كاملًا.

تطبق قواعد القفل والتحقق على جميع مسارات السداد ذات الصلة، بما فيها API القديم والمزامنة، وليس المسار الجديد وحده. تراجع العمليات الأخرى التي تغير المستحق مثل الإشعارات الدائنة ضمن سياسة التزامن نفسها.

- نفس `client_uuid` مع نفس البيانات: إعادة نتيجة العملية السابقة.
- نفس `client_uuid` مع بيانات مختلفة: تعارض دون تسجيل جديد.
- سدادان متزامنان: لا يتجاوز مجموعهما المبلغ المسموح بتحصيله.
- اختبار الأقفال على PostgreSQL؛ SQLite لا يثبت صحة التزامن الإنتاجي.

## 9. تجربة المستخدم والمزامنة

تظهر «ديون العملاء» في القائمة الأساسية لوضع المتجر للمستخدم المخوّل. تتضمن الشاشة البحث بالاسم والهاتف، المستحق والمتأخر وآخر سداد، كشف العميل، واختيار المستحقات أو توزيع السداد على الأقدم.

خطوات المستخدم: اختيار العميل ← إدخال مبلغ وطريقة السداد ← معاينة التوزيع ← التأكيد ← عرض السند.

في نقطة البيع يختار المستخدم عميلًا عند البيع الجزئي أو الآجل، ويظهر المتبقي بوضوح.

عند انقطاع الاتصال:

- يحفظ الطلب محليًا كعملية بانتظار المزامنة، لا كسداد مؤكد.
- تظل بيانات الجهاز معزولة حسب الشركة والمستخدم والفرع.
- يعيد الخادم التحقق من الأرصدة عند الاتصال.
- إذا سدد جهاز آخر المستحق، تبقى العملية للمراجعة ولا يعاد توزيعها بصمت على ديون مختلفة.
- لا ضمان لتشغيل التطبيق من الصفر دون اتصال ضمن هذه الميزة؛ يعتمد ذلك على قدرات التطبيق الحالية.

## 10. الصلاحيات والتكامل

- القراءة والتسجيل وفق صلاحيات المبيعات المعتمدة.
- الديون الافتتاحية والتصحيحات بصلاحية أضيق للمالك أو المسؤول المخوّل.
- التحقق من العزل في القوائم والكتابة والطباعة والتصدير والمزامنة.
- ربط التحصيل النقدي بآلية وردية الصندوق بعد مراجعة نموذجها الحالي، مع منع الحساب المكرر.
- استخدام قواعد البيانات البنكية الحالية للتحويلات المسجلة يدويًا.
- تحديث النسخ الاحتياطي والاستعادة وسجل التدقيق للنماذج الجديدة.

## 11. خطة التنفيذ والتقدير

التقدير لمهندس متفرغ، ويعاد تقديره بعد اعتماد القرارات المالية والتقنية. لا يمثل موعد تسليم ملزمًا قبل ذلك.

| المرحلة | المخرج ومعيار القبول | التقدير |
| --- | --- | --- |
| التحليل والتصميم | قواعد حساب وعقود API ومخطط بيانات معتمد | 1–2 يوم |
| القراءة وكشف الحساب | تطابق القائمة والكشف مع الفواتير والمدفوعات | 2–3 أيام |
| السداد والتوزيع | عملية ذرية ومنع تكرار وتعارض وسند طباعة | 3–4 أيام |
| الديون الافتتاحية | تسجيل وتصحيح وتسوية ونسخ احتياطي | 2–3 أيام |
| الواجهة والمزامنة والقبول | تجربة عربية وهاتف واختبارات تكامل وتزامن | 3–4 أيام |

الإجمالي: **11–16 يوم عمل**. التقدير يستبعد استيراد ملفات قديمة والتذكيرات الآلية ودفتر الموردين.

### المسؤوليات وبوابات القرار

- مدير المشروع: تثبيت النطاق والأولويات والتبعيات ومتابعة معايير القبول.
- مالك المنتج: اعتماد قواعد السداد والرصيد الدائن والديون الافتتاحية.
- مهندس البرمجيات: التصميم والخدمات والواجهة والترحيلات واختبارات التنفيذ.
- مسؤول الجودة أو المراجع: مراجعة السيناريوهات المالية والعزل والتزامن والقبول.

يمكن لشخص واحد أداء أكثر من دور، لكن تبقى قائمة المراجعة لكل دور منفصلة. تنفذ تغييرات الشيفرة في commits صغيرة، وتراجع الترحيلات وعقود API قبل بناء الأجزاء التابعة لها.

## 14. التسليم والتشغيل

1. تسليم شاشة القراءة وكشف الحساب أولًا.
2. تفعيل تسجيل السداد بعد اجتياز اختبارات الذرية والتزامن.
3. تفعيل الديون الافتتاحية بعد اعتماد قواعدها واختبار الاستعادة.
4. إرفاق سجل تغيير ودليل تشغيل مختصر ونتائج قبول لكل تسليم.
5. عند ظهور مشكلة بعد الإطلاق، يوقف إدخال العمليات الجديدة مع إبقاء السجلات المالية محفوظة. لا تستخدم إزالة الترحيلات كوسيلة لحذف حركات مالية مسجلة.

## تعريف الإنجاز

كل مبلغ في دفتر العميل مرتبط بمستند قابل للتتبع، وكل سداد يحتسب مرة واحدة فقط مهما تكرر الطلب أو تعددت الأجهزة. تتطابق الأرصدة في القوائم والكشوف والطباعة، وتنجح اختبارات الصلاحيات والعزل والتزامن والاستعادة قبل اعتماد الإصدار.
