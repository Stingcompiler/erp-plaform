## 1. الغرض وحدود الوثيقة

تحدد هذه الوثيقة ما يحتاجه فيزانو ليقدم تجربة SaaS تجارية كاملة: كيف تعرف الشركة الخدمة، وتختار عرضًا، وتسجل، وتبدأ العمل، وتدفع وتجدد، وكيف تدير المنصة هذه العلاقة دون الدخول تلقائيًا إلى بيانات الشركة التشغيلية.

تكمل الوثيقة [خطة الاشتراكات والنسخة المستقلة](subscriptions-and-standalone-technical-plan.md) و[القرار المعماري للتسليم المزدوج](adr/0001-dual-delivery-subscriptions.md). لا تستبدل الأساس المنفذ، ولا تعني أن الوظائف المقترحة موجودة بالفعل. تعتمد تفاصيل الإطلاق التجاري هنا على اكتمال رحلة الشركة واختبارها، وليس على وجود نماذج الاشتراكات فقط.

كتابة الوثيقة لا تغير الشيفرة أو قاعدة البيانات، ولا تعتمد أسعارًا أو شروطًا تجارية. القرارات الموسومة «مقترح» تحتاج حسمًا قبل تنفيذ الجزء الذي يعتمد عليها.

## 2. التقييم الحالي

فيزانو تطبيق ERP متعدد الشركات يحتوي على أساس للاشتراكات والترخيص المستقل. يمكن لهذا البناء أن يخدم SaaS؛ لا يتطلب ذلك تقسيمه إلى خدمات مصغرة. لكن رحلة الاشتراك التجارية والإدارة المركزية لم تكتمل بعد.

غياب التسجيل الذاتي أو الأسعار العامة وحده لا ينفي كون المنتج SaaS؛ يمكن بيع خدمة للشركات بمساعدة المبيعات وبأسعار تعاقدية. النقص الحالي هو غياب مسار متصل وواضح من طلب التسجيل حتى التشغيل والتجديد.

| المجال | الموجود بحسب مراجعة المشروع | الفجوة التي تعالجها الوثيقة |
|---|---|---|
| إدارة الأعمال | شركات وفروع وأقسام ووحدات تشغيلية وصلاحيات | الحفاظ عليها واختبار عدم تأثرها |
| الاشتراكات | خطط وإصدارات واشتراكات وفواتير ودفعات يدوية | استكمال رحلة الإنشاء والتفعيل والتجديد |
| لوحة المنصة | واجهة منفصلة وأجزاء لإدارة الاشتراكات والطلبات | أدوار محددة وإدارة دورة حياة الشركة |
| صفحة الهبوط | تعريف بالخدمة ونموذج طلب عرض | توضيح الباقات والتجربة وطلب تسجيل شركة |
| الطلبات | `PlatformLead` مستقل عن CRM الشركة | ربط الطلب بالموافقة وإنشاء الشركة |
| التسجيل | إنشاء أجزاء عبر واجهات إدارية | مسار متكامل ينشئ الشركة والمالك والتجربة مرة واحدة |
| التجربة | توجيه إلى الدخول عند غياب رابط عرض مستقل | بيئة عرض فعلية ورحلة تجربة شركة منفصلة |
| التحصيل | مراجعة إثبات وتوزيع دفعة | ربط التسوية باستحقاق الفترة ومنع التجديد المكرر |
| النسخة المستقلة | أساس رخصة وحزمة تشغيل وأدوات نقل | قبول تشغيلي فعلي قبل التسليم التجاري |

مواضع مرجعية للمراجعة: `backend/subscriptions/views.py`، `backend/core/entitlements.py`، `backend/accounts/`، `backend/org/`، وواجهات المنصة وصفحة الهبوط في `frontend/`. يعاد التحقق من التفاصيل عند بدء كل مرحلة لأن الشيفرة قد تتغير بعد هذه المسودة.

## 3. تعريف المنتج وطريقتا التسليم

**التوجه المقترح:** فيزانو منصة إدارة أعمال للشركات متعددة الأقسام والفروع، تشمل المبيعات والمشتريات والمخزون والموارد البشرية والرواتب والمتابعة المالية المتاحة فعليًا في المنتج. لا يوصف بأنه نظام محاسبي شامل أو متوافق قانونيًا مع كل الدول دون تحقق مستقل.

| الجانب | SaaS مستضاف | نسخة مستقلة |
|---|---|---|
| من يشغل الخادم؟ | مشغل فيزانو | الشركة أو جهة تتعاقد معها |
| العلاقة التجارية | اشتراك بخطة وفترة | رخصة واتفاق صيانة ودعم |
| إدارة الشركات المشتركة | لوحة منصة مركزية | غير متاحة كتجربة SaaS محلية |
| مالك الشركة | يدير شركته ومستخدميها واشتراكها | يدير شركته ورخصة تثبيتها |
| الشيفرة | نفس التطبيق ومخطط البيانات | نفس التطبيق ومخطط البيانات |
| اتصال الترخيص | حقوق اشتراك داخل الخدمة | تحقق محلي؛ لا اتصال يومي إلزامي |

استمرار دعم التسليمين مطلب قائم. اعتبار SaaS العرض الأساسي والنسخة المستقلة عرضًا تعاقديًا للشركات توصية تسويقية لم تعتمد بعد. ويجب تحديد التمييز عن منتج المستخدم الآخر الموجه للمتاجر والمخازن قبل كتابة الوعود التسويقية النهائية.

وضع المتجر/الشركة يبقى إعداد تشغيل للشركة يختاره مالكها. لا يغير طريقة النشر، ولا يحول الموظف إلى مدير منصة، ولا يمنح وحدة خارج حقوق الباقة.

## 4. المبادئ التي لا يجوز كسرها

- تبقى حسابات الشركات وبياناتها وإعداداتها محفوظة عند تغيير الخطة أو انتهاء الاشتراك.
- تبقى بيانات عملاء الشركة في CRM الشركة؛ طلبات الاشتراك في فيزانو تخص مشغل المنصة.
- فواتير اشتراك فيزانو مستقلة عن فواتير الشركة ومقبوضاتها ودفتر ديونها.
- الصلاحيات التجارية لا تتجاوز دور المستخدم أو نطاق شركته وفرعه أو قيود وضع المتجر.
- لا يستخدم `User.is_active` لتعليق اشتراك الشركة أو انتهاء تجربتها.
- جميع القرارات التجارية وتغييرات الأدوار تسجل بالفاعل والوقت والسبب، دون محو التاريخ المالي.
- الدفع يدوي فقط. لا بوابة دفع ولا تكامل خارجي للتحصيل ضمن هذا النطاق.
- يبقى Django تطبيقًا واحدًا مع الواجهة الحالية؛ لا Docker ولا إعادة بناء لوحدات الأعمال.
- عمليات الموظفين القابلة للمزامنة تستمر في احترام منع التكرار وحقوق الوصول عند وصول الطلب للخادم.

## 5. الأدوار والفصل بين المنصة والشركة

مصطلح «مالك المنصة» يعني مشغل فيزانو، و«مالك الشركة» يعني العميل المشترك. لا يورث أحدهما صلاحيات الآخر تلقائيًا.

| الدور المقترح | المسموح | غير الممنوح افتراضيًا |
|---|---|---|
| مالك المنصة | أدوار موظفي المنصة، الباقات، السياسات، ومتابعة النشاط التجاري | تصفح رواتب ومبيعات كل شركة |
| مسؤول المبيعات | متابعة طلبات التسجيل والتواصل والعروض | تأكيد السداد أو قراءة عمليات العميل |
| مدير الاشتراكات | الموافقة التجارية، الفواتير، مراجعة الدفع، التجديد والتعليق بسبب موثق | إدارة موظفي الشركة ومخزونها |
| مسؤول الدعم | بيانات الطلب والدعم وحالة الخدمة | دخول شركة دون تفويض محدود |
| مسؤول التشغيل | صحة الخدمة والنسخ والاستعادة وفق إجراءات تشغيل | تصفح بيانات الشركة من واجهة الأعمال |
| مالك الشركة | إعداد الشركة ودعوة الموظفين ووضع التشغيل والاشتراك | إدارة مشتركي المنصة الآخرين |
| مدير المالية بالشركة | أعمال المالية المصرح بها داخل الشركة | تغيير وضع الشركة أو إدارة اشتراكات المنصة |
| مدير الموارد وباقي الإدارات | وحداتهم وتقاريرهم بحسب الأدوار الحالية | بيانات خارج النطاق المسموح |

قد يجمع موظف منصة أكثر من دور بتكليف صريح ومسجل. لا يعتمد التصميم النهائي على شرط شامل من نوع `is_platform_admin` لفتح جميع عمليات الإدارة.

حساب Django superuser حساب تقني عالي الامتياز، وليس الدور اليومي لمدير الاشتراكات. يجب حصر استعماله وتدقيقه وعدم اعتبار إخفاء عناصر القائمة حماية كافية. الفصل يتحقق في API والاستعلامات وتنزيل الملفات والتصدير أيضًا.

لوحة المنصة تعرض بيانات تجارية محددة: اسم المشترك، جهة الاتصال، الخطة، الفترة، حالة السداد، واستهلاك الحدود. لا تستدعي تقارير أعمال الشركات. الاستعلامات المركزية استثناء مقصود للبيانات التجارية فقط، مع صلاحيات صريحة؛ لا تزال كل استعلامات الأعمال مقيدة بالشركة.

**دعم العميل:** لا ينفذ انتحال حساب المالك في الإصدار الأول. يبدأ الدعم دون دخول بياناته؛ وأي وصول لاحق يحتاج موافقة المالك، ونطاقًا ومدة، وقراءة فقط افتراضيًا، وسجلًا ظاهرًا للعميل وإمكانية إلغاء التفويض.

## 6. رحلة الزائر والتسجيل المقترحة

**المسار الأول المقترح: تسجيل بمساعدة فريق المنصة.** يسمح بمراجعة الشركة وتجهيزها مع بقاء الاشتراك والتفعيل داخل فيزانو. التسجيل الذاتي الكامل مرحلة لاحقة، وليس شرطًا لبدء بيع SaaS للشركات.

1. يقرأ الزائر صفحة المنتج والباقات وطريقة الاستضافة.
2. يختار «اطلب تجربة لشركتك»، أو «جرّب العرض التوضيحي»، أو «اطلب نسخة مستقلة».
3. يرسل طلبًا منظمًا ويحصل على رقم متابعة ورسالة نجاح واضحة.
4. يتابع مسؤول المبيعات الطلب؛ ويحدد العرض والباقة والشروط المتفق عليها.
5. يوافق صاحب الصلاحية على تجهيز الشركة، بعد التحقق من البريد وهوية جهة التواصل بالآلية المعتمدة.
6. ينشئ النظام الشركة والمالك والتهيئة الأساسية واشتراك التجربة مرة واحدة.
7. تصل دعوة آمنة إلى المالك لتفعيل حسابه واختيار كلمة المرور.
8. يكمل المالك إعداد الشركة ثم يستخدمها ضمن حقوق التجربة.
9. تصدر فاتورة الاشتراك ويقدم المالك إثبات سداد يدويًا.
10. يراجع مدير الاشتراكات السداد؛ وعند اكتمال تسوية الفاتورة تمنح الفترة المتفق عليها مرة واحدة.

### بيانات طلب التسجيل

| الحقل | القاعدة المقترحة |
|---|---|
| اسم الشركة واسم جهة الاتصال | مطلوبان |
| بريد العمل | مطلوب؛ قابل للتحقق قبل تفعيل الوصول |
| الهاتف مع رمز الدولة | مطلوب لمسار المبيعات المقترح |
| الدولة والمنطقة الزمنية | الدولة مطلوبة؛ يؤكد المالك المنطقة الزمنية خلال الإعداد |
| حجم الشركة | نطاق تقريبي للمستخدمين والفروع، دون جمع بيانات الموظفين |
| الباقة المطلوبة | اختيار من الباقات المنشورة أو «أحتاج مساعدة» |
| طريقة التسليم | SaaS أو نسخة مستقلة |
| ملاحظات | اختيارية ومحدودة الطول |
| إقرار الخصوصية | يسجل إصدار النص والوقت؛ التسويق اختياري ومستقل |

لا يطلب النموذج كلمة مرور أو رقم حساب بنكي. لا ينشئ العميل شركة بمجرد اختيار رمز باقة غير منشورة. التحقق من الباقة يتم في الخادم.

استجابة الطلب العام لا تكشف إن كان البريد يخص حسابًا قائمًا. يطبق منع الإساءة وحدود الطلبات ومفتاح منع التكرار. لا يعتمد منع تكرار الشركة على تشابه الاسم وحده؛ تظهر حالات الاشتباه للمراجع.

### حالات الطلب

`submitted → under_review → approved → provisioned`

يمكن الانتقال من المراجعة إلى `needs_information` ثم العودة إليها، أو إلى `rejected` مع سبب داخلي. السحب `withdrawn` ينهي الطلب قبل التجهيز. بعد التجهيز يعالج التعليق من دورة الاشتراك لا بإعادة الطلب إلى حالة سابقة.

فشل التجهيز يسجل كمحاولة فاشلة قابلة للإعادة، مع بقاء الطلب المعتمد؛ لا ينشئ شركة ثانية. ولا يقبل تغيير الحالة مباشرة دون فحص الانتقال وصلاحية الفاعل.

## 7. تجهيز الشركة ودعوة المالك

تنفذ خدمة واحدة داخل معاملة قاعدة بيانات: قفل الطلب المعتمد، والتحقق من عدم تجهيزه سابقًا، وإنشاء الشركة والمالك والفرع الرئيسي والإعدادات الافتراضية واشتراك التجربة المحدد، وربط الطلب بالشركة، ثم تسجيل الحدث.

يجب فصل التحقق من البريد عن بدء مدة التجربة: **المقترح** بدء التجربة عند قبول دعوة المالك، لا عند انتظار إرسال البريد. تكون الشركة قبل ذلك قيد التفعيل ولا تمنح وصول أعمال؛ ويستدعي اعتماد هذا السلوك مراجعة نموذج الحالات القائم قبل أي migration.

ترسل الدعوة بعد نجاح المعاملة عبر سجل إرسال دائم يعاد تشغيله عند الفشل. فشل البريد لا يعيد إنشاء الشركة. يعرض المشغل حالة الإرسال وخيار إعادة الإرسال؛ وتلغى صلاحية الدعوة السابقة عند استبدالها.

رمز الدعوة عشوائي، محدود المدة، للاستخدام مرة واحدة، ويحفظ بصمته فقط. لا تظهر كلمة مرور المالك لموظفي المنصة. إذا كان البريد مرتبطًا بحساب قائم، يعالج الربط عبر مسار موثق؛ لا يغير النظام شركة الحساب أو ينشئ هوية متعارضة بصمت.

تهيئة المالك تشمل: اسم الشركة، العملة، الدولة، المنطقة الزمنية، بيانات الفرع، الملف الضريبي المتاح، ودعوة موظفين ضمن الباقة. لا يقدم اختيار دولة على أنه إثبات امتثال قانوني. يمكن حفظ التقدم واستكماله دون إعادة التهيئة.

## 8. التجربة التوضيحية وتجربة الشركة

| النوع | الغرض | البيانات والوصول |
|---|---|---|
| عرض توضيحي عام | فهم المنتج قبل التواصل | بيئة منفصلة وبيانات مصطنعة؛ قراءة فقط في الإصدار الأول |
| تجربة خاصة للشركة | تقييم العمل الحقيقي | شركة معزولة ومالك ودعوات وحدود ومدة واضحة |

العرض العام لا يعرض حساب مدير منصة ولا يسمح برسائل بريد خارجية أو رفع مستندات حقيقية أو تصدير بيانات إنتاج. تظهر عبارة «بيانات تجريبية» بوضوح. لا يعاد استخدام مستأجر إنتاج لهذا الغرض.

الانتقال من تجربة الشركة إلى الاشتراك يحافظ على نفس الشركة والبيانات. لا تنسخ البيانات إلى شركة جديدة عند الدفع. مدة 14 يومًا والسماح 7 أيام اقتراحان قابلان للضبط، وليسا قرارًا تجاريًا معتمدًا.

## 9. الباقات والتسعير

الأسماء التالية تصور للنقاش وليست باقات مفعلة:

| الباقة | التوجه المقترح | ما يلزم تحديده |
|---|---|---|
| Core | المبيعات والمشتريات والمخزون والمتابعة المالية المتاحة | المقاعد والفروع والمخازن والسعر |
| Business | Core مع الموارد البشرية والرواتب وCRM والتقارير المرتبطة | الحدود والتدريب والدعم |
| Enterprise | احتياجات أوسع وخدمات إعداد ونقل ودعم متفق عليها | عرض سعر؛ خيار مستقل بعقد منفصل |

يجب بناء مصفوفة وحدات وتبعيات قابلة للتطبيق قبل نشر الباقات. لا يعلن عن وحدة لم تختبر، ولا تخفى تكلفة إلزامية ضمن عبارة «يبدأ من».

كل عرض منشور يوضح: العملة، السعر والدورة، هل الضرائب مشمولة، الحدود، الوحدات، رسوم الإعداد إن وجدت، نطاق الدعم، التجربة، وطريقة التجديد اليدوية. عند عدم اعتماد أرقام يستخدم «اطلب عرض سعر» صراحة، ولا يعرض سعرًا وهميًا أو صفرًا.

يعتمد العميل إصدار سعر محفوظًا؛ تغيير سعر الباقة المنشورة لا يعدل فواتيره أو عقده السابق. يحسم قبل الإطلاق موعد تطبيق السعر الجديد على التجديد، والإشعار المطلوب، وسياسة التخفيض والاسترداد. لا ينفذ احتساب تلقائي لفروقات منتصف الدورة في الإصدار الأول.

| حالة الاشتراك الحالية المستهدفة | السلوك المطلوب |
|---|---|
| `trialing` | حقوق تجربة حتى نهاية محددة |
| `active` | حقوق الفترة المدفوعة أو الاتفاق المسجل |
| `grace` | استمرار مؤقت حتى نهاية سماح صريحة مع تنبيه المالك |
| `read_only` | قراءة وتصدير ضمن صلاحيات المستخدم؛ منع أعمال جديدة |
| `suspended` | تعليق بسبب موثق؛ يبقى مسار المالك لمعالجة الاشتراك حسب سبب التعليق |
| `cancelled` | انتهاء الاشتراك دون حذف بيانات تلقائي |

التجربة تنتهي إلى السماح إن كان ممنوحًا ثم القراءة فقط. الفترة النشطة تتبع السياسة نفسها إذا لم تجدد. التعليق الإداري لا يرفع تلقائيًا بمجرد وصول دفعة دون التحقق من سبب التعليق. الإلغاء المجدول يبقي الحقوق حتى نهاية الفترة المدفوعة ثم يطبق الأثر المتفق عليه.

تحسب الحقوق الفعلية من وقت الخادم والتواريخ حتى لو تعطلت المهام المجدولة. يجب تغطية انتهاء تجربة دون وجود فترة مدفوعة، ومنع اعتبار قائمة وحدات فارغة تصريحًا بكل الوحدات.

### التحصيل والتجديد

1. تصدر فاتورة مرتبطة بالشركة وإصدار الباقة والفترة ومبلغ وعملة ثابتين.
2. يرفع المالك إثبات التحويل ومرجعه؛ تبقى الدفعة قيد المراجعة.
3. يشاهد مدير الاشتراكات الإثبات عبر تنزيل محمي، ويتحقق يدويًا من الاستلام.
4. تعتمد الدفعة وتوزع على فواتير نفس الشركة والعملة ضمن المبلغ المتاح.
5. عند تسوية فاتورة الفترة بالكامل، ينشأ حدث منح الفترة مرة واحدة داخل معاملة مقفلة.
6. يرسل إشعار للمالك بنتيجة المراجعة وتواريخ الاستحقاق الجديدة.

الدفعة الجزئية لا تمنح فترة كاملة تلقائيًا؛ والاستثناء يحتاج حقًا تجاريًا صريحًا محدود المدة. لا يمنح مجرد رفع الإثبات حقوقًا إضافية. التصحيح المالي بسجل مقابل، دون تعديل تاريخ الدفعة المعتمدة.

التجديد المبكر يبدأ من نهاية الفترة الحالية؛ والمتأخر من تاريخ إعادة التفعيل ما لم توجد فترة تعاقدية صريحة معتمدة. يجب أن تشير الفاتورة وحدث الاستحقاق إلى الفترة نفسها. إعادة الطلب أو تشغيل المهمة أو مراجعة الدفعة بالتزامن لا تمدد المدة مرة ثانية.

## 11. الشاشات المطلوبة

### الواجهة العامة

صفحة هبوط توضح الجمهور والوظائف المتاحة والتسليمين، ومقارنة الباقات، وأسئلة الاشتراك والتجربة، وروابط الخصوصية والشروط والتواصل. أزرار مستقلة للدخول، وطلب تجربة شركة، والعرض التوضيحي، والنسخة المستقلة. صفحة نجاح الطلب تعرض رقم المتابعة والخطوة التالية دون وعد بموعد استجابة غير معتمد.

### لوحة المنصة

- نظرة عامة تجارية: الطلبات الجديدة، شركات تنتظر التفعيل، تجارب قاربت الانتهاء، دفعات تنتظر المراجعة، واشتراكات تحتاج متابعة.
- طلبات التسجيل: فلاتر وحالة ومسؤول متابعة وسجل ملاحظات وموافقة وتجهيز.
- المشتركون: قائمة وملف تجاري لكل شركة وخطتها وفترتها وحدودها وسجل قراراتها.
- الباقات: إعداد إصدار ومسودة ونشر وأرشفة؛ لا تعديل إصدار مستخدم بما يغير العقد.
- الفواتير والدفعات: إصدار ومراجعة إثبات وتوزيع وتسوية وتصحيح مسجل.
- فريق المنصة: منح أدوار محددة وتدقيق التغييرات.
- التشغيل: حالة الإرسال والمهام والفشل القابل للإعادة، دون عرض تقارير أعمال الشركات.

لا تعرض مؤشرات مثل الإيراد الشهري المتكرر قبل تعريف احتسابه للعملات والدورات والإلغاءات. يبدأ الإصدار الأول بأعداد الحالات والمبالغ المحصلة مفصولة بالعملة.

### مساحة مالك الشركة

تهيئة أولية، وحالة الاشتراك والخطة والحدود والفترة، والفواتير وإثبات الدفع ونتيجة المراجعة، وطلب التجديد أو تغيير الخطة، ووسيلة دعم. رسائل انتهاء التجربة موجهة للمالك؛ الموظف يرى سبب تعذر العملية وطلب التواصل مع مالكه دون تفاصيل مالية تجارية.

## 12. التصميم التقني المقترح

يعاد استخدام `Plan` و`PlanVersion` و`Subscription` والفواتير والمدفوعات وخدمة الحقوق. لا تنشأ منظومة اشتراكات موازية.

| الإضافة المنطقية | المسؤولية |
|---|---|
| طلب تسجيل شركة | البيانات المنظمة والحالة والباقة وطريقة التسليم وربط الشركة بعد التجهيز |
| محاولة تجهيز | مفتاح منع التكرار والنتيجة والخطأ التشغيلي دون أسرار |
| دعوة مالك | بصمة الرمز وانتهاؤه وقبوله وإبطاله |
| إسناد دور منصة | صلاحيات تجارية مركزية محددة |
| سجل إرسال دائم | إشعارات قابلة للإعادة مع منع التكرار وحالة التسليم |
| حدث منح فترة | ربط تسوية الفاتورة بالفترة التجارية دون منح مكرر |

هذه مسؤوليات مقترحة وليست أسماء نماذج ملزمة. يفحص التصميم التفصيلي ما يمكن إعادة استخدامه، ويعرض أي تعديل لنموذج قائم قبل تنفيذه. يبدأ بترحيلات إضافية ولا يغير هوية حسابات الشركات الموجودة.

تبقى `PlatformLead` لطلبات الاستفسار والعرض الحالية، ويربط طلب التسجيل بها عند التحويل إن لزم؛ لا تحول كل رسالة تواصل قديمة تلقائيًا إلى شركة أو تجربة.

### عقود API مقترحة

| المسار المنطقي | الغرض والحماية |
|---|---|
| `GET /api/public/plans/` | الباقات المنشورة والبيانات التسويقية فقط |
| `POST /api/public/registration-requests/` | استقبال طلب محدود المعدل وآمن من التكرار |
| `POST /api/public/owner-invitations/accept/` | قبول رمز صالح مرة واحدة وإنشاء وصول المالك |
| `/api/platform/registration-requests/` | مراجعة الطلبات لصاحب الدور |
| `POST .../{id}/approve/` و`.../{id}/provision/` | انتقالات صريحة مسجلة وقابلة لإعادة الطلب بأمان |
| `/api/platform/tenants/` | بيانات الاشتراك التجارية دون موارد الأعمال |
| واجهات الاشتراك الحالية | استكمال الفواتير والتسوية والتجديد بدل تكرارها |

المسارات إرشادية وتطابق أسلوب المشروع عند التنفيذ. تغيير حالة أو خطة لا ينفذ بعملية قراءة. الخادم يتحقق من CSRF والمصادقة وصلاحية العملية والنطاق وفق آلية المشروع، ولا يعتمد على قيود الواجهة.

## 13. الإشعارات والتشغيل والاحتفاظ

الإشعارات المطلوبة: استلام الطلب، طلب معلومات، دعوة المالك، فشل إرسال الدعوة للمشغل، قرب نهاية التجربة والفترة، إصدار فاتورة، قبول/رفض إثبات، والتعليق أو إعادة التفعيل. لكل إشعار مفتاح يمنع الإرسال المتكرر؛ ولا تسجل الرموز أو كلمات المرور في السجلات.

التنبيهات داخل التطبيق تستمر في إظهار حالة الاشتراك الحالية حتى لو قرأ المستخدم الإشعار؛ قراءة الإشعار تخفي عنصر المتابعة الشخصي ولا تغير الحالة التجارية.

قبل الإطلاق يجب تحديد مسؤول الدعم وساعات الخدمة، ومسؤول النسخ والاستعادة، ووجهة الإرسال، وسياسة الاحتفاظ بعد الإلغاء ووسيلة التصدير. لا حذف تلقائي ضمن هذه المرحلة. تحدد أهداف الاستعادة وفقد البيانات المقبولة ثم تثبت بتجربة استعادة فعلية؛ لا تحول التقديرات إلى وعود تسويقية.

## 14. خطة التنفيذ وترتيب الاعتماد

| المرحلة | الناتج | شرط القبول |
|---|---|---|
| 0 — تثبيت القرارات | حسم سجل القرارات أدناه وتفصيل النموذج والصلاحيات | لا تضارب بين السياسة التجارية والحقوق القائمة |
| 1 — إغلاق فجوات الأساس | مراجعة تجاوزات إدارة المنصة، تسجيل إنشاء الاشتراك، حالات الوقت والتسوية والتوجيه بعد الدخول | اختبارات API تثبت الفصل ومنع تكرار منح الفترة |
| 2 — التسجيل والتجهيز | الطلب والمراجعة والخدمة الذرية والدعوة وإعداد المالك | طلب واحد ينتج شركة واحدة ومالكًا وتجربة، مع نجاح إعادة المحاولة |
| 3 — الاشتراك التجاري | إدارة الباقات والفواتير وإثبات الدفع والتفعيل والتجديد والتنبيهات | رحلة كاملة من التجربة إلى التجديد والتعليق والاستعادة |
| 4 — تجربة الزائر | صفحة هبوط وباقات منشورة ونموذج وعرض توضيحي منفصل | الزائر يفهم العرض ويكمل الطلب دون دخول حساب قائم |
| 5 — إطلاق تجريبي | نشر مرحلي واختبارات PostgreSQL واستعادة ودليل تشغيل | اجتياز قبول رحلة الشركة والعزل والتعافي |

يراجع ضمن المرحلة 1 موضع تسجيل نشاط إنشاء الاشتراك في `backend/subscriptions/views.py` الذي ظهر بعد `return` في المراجعة، وكذلك إعادة قيمة الجلسة لمسار التوجيه بعد الدخول. هذه عناصر تحقق وإصلاح، وليست ادعاء بإصلاحها ضمن الوثيقة.

لا يقدر موعد الإطلاق قبل تفصيل القصص وحسم القرارات. لكل مرحلة مراجعة مستقلة وسجل اختبارات؛ ولا يعلن اكتمال SaaS بمجرد نجاح بناء الواجهة.

### إدخال التغييرات بأمان

- تحفظ الشركات الحالية وحقوق `legacy` دون تحويلها إلى تجارب أو إنشاء مالكين جدد لها.
- يبدأ مسار التسجيل خلف إعداد تفعيل مستقل، ولا يغير مسار الدخول القائم للشركات.
- تبقى سياسة الحقوق `disabled/observe/enforce` مستقلة؛ لا تفعل `enforce` عالميًا قبل اختبار أثرها.
- يمنع إصدار تسجيل عام تجاري بينما حقوق الشركات الجديدة غير مطبقة؛ تعالج آلية التفعيل التدريجي صراحة قبل الإطلاق.
- يوقف مسار التسجيل الجديد عند الحاجة دون حذف شركات أنشئت أو فواتير ودفعات سجلت.
- تظل واجهات التسجيل التجاري للمنصة غير متاحة في النشر المستقل، مع استمرار تهيئته وترخيصه المحلي.
- لا تغير migrations أو نشر واجهة وحدهما وضع المتجر أو صلاحيات موظفي الشركات.

## 15. اختبارات القبول المطلوبة

| السيناريو | النتيجة المطلوبة |

| فشل البريد بعد التجهيز | إعادة إرسال، دون إعادة تجهيز |
| دعوة منتهية أو مستعملة أو مستبدلة | رفض واضح وآمن |
| بريد مالك مستخدم سابقًا | معالجة تعارض دون نقل حساب أو كشفه للعامة |
| نهاية تجربة/سماح مع توقف المجدول | الحقوق الصحيحة محسوبة عند الطلب |
| دفعة جزئية أو إثبات غير معتمد | لا تمديد كامل غير مستحق |

| تجديد مبكر ومتأخر وإلغاء مجدول | تواريخ متسقة مع الفاتورة والسياسة |
| تخفيض باقة فوق الاستخدام | لا حذف ولا تعديل صلاحيات عشوائي |
| إعادة عملية offline ناجحة بعد الانتهاء | إعادة نتيجتها دون أثر مكرر؛ العملية الجديدة تفحص الحقوق |
| شركات قائمة قبل الترحيل | استمرار الوظائف والحقوق والبيانات |

| العرض العام | بيانات مصطنعة فقط دون اتصال ببيانات الإنتاج |
| العربية والجوال | RTL ورسائل مفهومة وروابط تنقل صحيحة |
| النسخ والاستعادة | استعادة فعلية للقاعدة والوسائط وتحقق من شركة معزولة |

تشمل اختبارات الانحدار المبيعات والمخزون والمرتجعات والديون والرواتب وتقارير الأدوار. تختبر الأقفال والتزامن على PostgreSQL؛ نجاح SQLite لا يكفي لإثباتها. ترفق نتائج فعلية لكل مرحلة، لا مجرد قائمة سيناريوهات.

## 17. تعريف اكتمال الإصدار التجاري الأول

يستطيع زائر فهم عرض فيزانو وطلب تجربة لشركته، ويستطيع موظف منصة مخول مراجعة طلبه وتجهيز شركة معزولة دون تدخل يدوي في قاعدة البيانات. يفعل المالك حسابه ويكمل الإعداد ويستخدم وحداته، ثم يسدد يدويًا وتجدد حقوقه مرة واحدة. يستطيع مشغل المنصة متابعة الاشتراك دون الاطلاع على أعمال العميل، وتبقى بياناته محفوظة عند الانتهاء. تعمل النسخة المستقلة من نفس المنتج دون اعتماد على رحلة SaaS.

لا يعد الإصدار مكتملًا قبل اجتياز الاختبارات التشغيلية والوظيفية وتوثيق حدود الدعم والقرارات التجارية. التسجيل الذاتي الفوري، وبوابات الدفع، وانتحال حسابات العملاء، والمحاسبة الشاملة، وإعادة بناء التطبيق كخدمات مصغرة خارج نطاق هذه الخطة.
