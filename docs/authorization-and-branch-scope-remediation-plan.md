# مراجعة الصلاحيات وخطة إصلاح نطاق الشركة والفروع

**التاريخ:** 13 سبتمبر 2026

**الحالة:** تنفيذ مرحلتي الحماية والحَوكمة، ومعظم نطاق الموارد المكتملة في 13 سبتمبر 2026. تبقى موارد لا تحمل مفتاح فرع وتتطلب ترحيل بيانات مدروس قبل إغلاق الخطة بالكامل.

## تحديث التنفيذ — 13 سبتمبر 2026

نُفذت الحدود الآتية في الخادم والواجهة مع اختبارات تغطي الحالات السلبية:

- حساب المنصة لا يرث أي صلاحية تشغيلية للشركات، حتى لو كان مدير منصة؛ واجهات المنصة تبقى منفصلة عن بيانات العملاء.
- المستخدم بلا دور، أو المستخدم الفرعي بلا فرع صالح ونشط، يُرفض دخوله ولا يحصل على fallback لبيانات الشركة.
- الدور غير المعروف يساوي `none` في جميع الوحدات إلى أن يحصل على سياسة معتمدة صراحة.
- المالك يستطيع إنشاء مالك إضافي داخل الشركة. لا يمكن تعطيل أو تخفيض آخر مالك نشط، ولا يمكن للمستخدم تعديل دوره أو تعطيل نفسه.
- المدير العام يملك إدارة تشغيلية كاملة للشركة وفروعها، لكنه لا يعيّن مالكًا ولا يحرر حساب مالك. تبقى الملكية والاشتراك للمالك.
- مدير الفرع يدير مستخدمي فرعه فقط وبأدوار فرعية، ولا ينشئ مدير فرع أو مديرًا عامًا أو مالكًا، ولا ينشئ أو يحذف فرعًا.
- نطاق الفرع صارم في المخزون والمبيعات والمرتجعات وCRM وHR والتقارير والمزامنة وملخصات لوحة التحكم؛ لا تُعرض صفوف `NULL` التشغيلية تلقائيًا لمدير الفرع.
- أعادت واجهة الجلسة قدرات دقيقة، وتستخدم صفحة المستخدمين تلك القدرات لإخفاء الأفعال غير المسموح بها، مع بقاء الحماية الحاسمة في الخادم.

### المتبقي الذي يتطلب تعديل نموذج البيانات وترحيلًا

لا يجوز ادعاء عزل فرعي كامل في الموارد الآتية قبل إضافة مفتاح فرع وترحيل السجلات الحالية، لأن نموذجها الحالي يعمل على مستوى الشركة فقط:

1. العملاء والموردون: لا يحمل أي منهما فرعًا مباشرًا. يمكن التعامل معهم كسجل مشترك للشركة، أو إضافة `branch` وتحديد ملكية كل سجل؛ الاختيار التجاري مطلوب قبل الترحيل.
2. فواتير الموردين ومدفوعات الموردين وبعض سجلات المالية: لا تحمل مسار فرع موثوقًا. لذلك لا تعرض لوحة التحكم مجاميعها لمدير الفرع، لكن إتمام عزل endpoint الخاص بها يحتاج مفتاح فرع وسياسة ترحيل.
3. السجلات التاريخية غير المسندة (`branch=NULL`): لا تُنسب تلقائيًا. تُخرج إلى قائمة معالجة يراجعها المالك أو المدير العام ثم تُسند بدليل تشغيلي.
4. الأدوار المخصصة: القاعدة الحالية آمنة (منع افتراضي)، لكن دعمها بصورة كاملة يحتاج permission codes للعملية والصف الواحد بدل الاعتماد على `scope_level`.

هذه ليست فجوات مسموحًا بها؛ هي المرحلة التالية المقصودة، وتحتاج migration منفصلة وخطة استعادة ونسخة احتياطية، وفق قواعد المشروع.

## 1. الهدف

إعادة بناء سياسة الصلاحيات حول ثلاث طبقات واضحة:

1. **مالك الشركة:** سلطة الملكية وإدارة أعلى مستوى داخل شركته، ويمكن وجود أكثر من مالك.
2. **المدير العام:** سلطة تنفيذية على الشركة كلها وكل فروعها.
3. **مدير الفرع:** سلطة تشغيلية داخل فرعه فقط، ولا يقرأ أو يعدل بيانات فرع آخر.

تبقى هوية مشغل منصة فيزانو منفصلة عن هويات الشركات. صلاحية إدارة الاشتراكات لا تعني صلاحية قراءة مبيعات أو رواتب أو مخزون الشركات.

## 2. الحكم الحالي

العزل بين **الشركات** موجود كأساس مشترك في `CompanyScopedQuerySetMixin`، وتوجد مصفوفة وحدات مركزية في `core/rbac.py`. لكن نطاق الفرع اختياري ويعمل بأسلوب يسمح عند نقص التعيين، وأدوار المنصة مجمعة تحت تجاوز شامل. لذلك لا تكفي البنية الحالية لتحقيق السياسة المطلوبة بأمان.

إنشاء مالك ثانٍ ممكن حاليًا لمالك يملك كتابة وحدة المستخدمين، لأن `UserSerializer` يقبل دور `Business Owner`. لكن لا توجد ضوابط تمنع تعطيل آخر مالك نشط، أو تغيير دور الذات، أو إسناد أدوار تنفيذية عالية بواسطة دور مخصص حصل على صلاحيات واسعة من fallback.

## 3. النتائج مرتبة حسب الخطورة

### P0 — حرج

#### 3.1 مدير المنصة يستطيع تجاوز حدود بيانات الشركات

- `User.is_platform_admin` يصبح صحيحًا للسوبر أدمن أو لحساب بلا شركة ودور platform.
- `CompanyScopedQuerySetMixin.get_queryset()` يعيد الاستعلام كاملًا لمستخدم المنصة.
- `RoleModuleAccess` يمنح مستخدم المنصة كتابة كل وحدات الأعمال.
- النتيجة: فصل لوحة المنصة في الواجهة لا يمنع حساب المنصة من طلب APIs المخزون والمبيعات والرواتب لكل الشركات.

**الإصلاح:** منع هويات المنصة من جميع APIs التشغيلية للشركات افتراضيًا. تنشأ صلاحيات منصة محددة مثل التسجيل، الاشتراكات، الفوترة، الدعم والتشغيل، ولا تمنح أي منها تجاوز بيانات الأعمال. يبقى superuser للاستخدام التقني عبر Django Admin وإجراءات طوارئ مدققة، لا كحساب تشغيل يومي.

#### 3.2 مستخدم الفرع غير المرتبط بفرع يرى بيانات الشركة بدل رفضه

- `_branch_scope()` يعيد `None` عند غياب `user.branch_id`.
- `None` يعني إلغاء ترشيح الفرع، ويوجد اختبار حالي يثبت أن المستخدم الفرعي بلا فرع يرى كل المستودعات.

**الإصلاح:** سياسة fail closed. كل دور `scope_level=branch` يجب أن يرتبط بفرع نشط من شركته. قبل إصلاح البيانات القديمة، يمنع تسجيل دخوله أو تعيد APIs قائمة فارغة مع رمز إعداد واضح. يمنع إنشاء أو تعديل مستخدم فرعي دون فرع.

#### 3.3 المستخدم بلا دور يحصل على قراءة واسعة

- `level_for(None, module)` يعيد `READ`.
- النتيجة: الحساب الذي فقد دوره أو أنشئ دون دور يستطيع قراءة عدة وحدات بحسب نطاق الشركة.

**الإصلاح:** الدور المفقود يساوي `NONE` لكل الوحدات. لا ينشأ مستخدم شركة بلا دور، وتوجد مهمة تدقيق للبيانات القديمة.

### P1 — عالٍ

#### 3.4 نطاق الفرع غير مطبق مركزيًا على جميع الموارد

`branch_field` اختيار يدوي لكل ViewSet. هو موجود للمستودعات والعملاء المحتملين والموظفين وبعض مستندات البيع والشراء، لكنه غير موجود أو غير مباشر في موارد تشغيلية أخرى، ومنها:

- حركات ودفعات وتسويات المخزون المرتبطة بمستودع.
- دفعات المبيعات وحركات الصندوق المرتبطة بفاتورة أو جلسة فرع.
- الاستلامات والفواتير ومدفوعات الموردين المرتبطة بأمر أو مستودع أو مورد.
- المرتجعات والإشعارات الدائنة والمدينة المرتبطة بمستند أصلي.
- الحضور والإجازات والسلف والخصومات والمستندات المرتبطة بموظف.
- المتابعات والملاحظات المرتبطة بعميل محتمل.
- المزامنة والتصدير والتقارير والملخصات المشتقة.

وجود `company_id` صحيح لا يمنع تسرب بيانات فرع إلى فرع آخر داخل الشركة.

**الإصلاح:** تعريف مركزي لمسار الفرع لكل مورد، مثل `branch`, `warehouse.branch`, `invoice.branch`, `employee.branch` أو `lead.branch`. يمنع تسجيل أي endpoint خاص ببيانات الفروع بلا تعريف صريح: `shared` أو مسار فرع. تطبق السياسة على list/detail/actions/files/CSV/sync/dashboard والتقارير.

#### 3.5 مدير الفرع لا يملك حاليًا أدوات إدارة فرعه

المصفوفة تمنحه تشغيل المبيعات والمشتريات والمخزون وCRM وقراءة HR، لكنها تمنعه من وحدتي `org` و`users`. لذلك لا يستطيع إدارة موظفي وحسابات فرعه رغم وصفه كمدير فرع.

**الإصلاح المستهدف:** إضافة عمليات محددة لا كتابة كاملة للوحدة:

- قراءة ملف فرعه فقط وتحديث حقول تشغيلية آمنة مثل الهاتف والعنوان.
- قراءة مستخدمي وموظفي فرعه فقط.
- إنشاء أو تعديل أدوار فرعية مسموح بها داخل فرعه.
- منع إنشاء مالك أو مدير عام أو مدير فرع آخر، ومنع نقل مستخدم إلى فرع آخر.
- منع تعطيل نفسه ومدير أعلى منه وإغلاق الفرع أو أرشفته.

#### 3.6 المدير العام ليس مساويًا للمالك في النظام الحالي

المدير العام يملك تشغيل معظم الوحدات، لكنه يملك قراءة فقط للمستخدمين والتنظيم والإعدادات. ولا يستطيع تغيير وضع النظام أو إدارة الاشتراك لأن هذه المسارات تتحقق من اسم `Business Owner` مباشرة.

**السياسة المقترحة:** مساواة تشغيلية كاملة بين المالك والمدير العام على كل الفروع، مع إبقاء أفعال الملكية التالية للمالك فقط: تعيين أو إزالة مالك، إدارة اشتراك فيزانو، وإغلاق الشركة. تغيير وضع المتجر كان متطلبًا سابقًا للمالك فقط؛ إذا أُريدت مساواة حرفية، يجب اعتماد نقله أيضًا للمدير العام صراحة قبل التنفيذ.

#### 3.7 fallback للأدوار المخصصة يمنح صلاحيات واسعة

أي دور غير معروف بنطاق `business` يحصل حاليًا على `WRITE` لكل الوحدات. هذا يسمح لدور مخصص أو خاطئ بأن يصبح مديرًا شاملًا، بما في ذلك إدارة المستخدمين.

**الإصلاح:** default deny. الدور غير الموجود في سياسة معتمدة لا يحصل على شيء. عند دعم الأدوار المخصصة، تستخدم علاقة `Role.permissions` الفعلية مع صلاحيات عمليات محددة، ولا يُستنتج الوصول من `scope_level` وحده.

#### 3.8 إدارة المالكين بلا قواعد استمرارية

لا توجد قاعدة خدمة تضمن وجود مالك نشط واحد على الأقل، ولا تمنع المالك من تغيير دور نفسه عبر PATCH، ولا توجد عملية مخصصة ومؤكدة لتعيين مالك جديد.

**الإصلاح:** مسار صريح `assign-owner` داخل معاملة وقفل للشركة، مع سجل تدقيق وسبب. يسمح بتعدد المالكين، ويمنع تعطيل أو تخفيض رتبة آخر مالك نشط. تغيير الملكية لا يتم بتعديل عام لحقل `role`.

### P2 — متوسط

#### 3.9 الصلاحية معرفة على مستوى الوحدة أكثر من العملية

قيم `read/write/none` لا تفرق بين إنشاء موظف، رؤية راتبه، قبول إجازة، اعتماد كشف راتب، أو تنزيل تقرير طبي. وهذا يمنح أحيانًا مساحة أكبر من حاجة الوظيفة.

**الإصلاح:** صلاحيات عمليات مثل:

- `users.view_branch`, `users.manage_branch`, `users.assign_executive_role`.
- `hr.view_profile`, `hr.view_compensation`, `hr.view_medical`, `hr.approve_leave`, `hr.run_payroll`.
- `finance.record`, `finance.approve`, `finance.report`.
- `org.manage_branch`, `org.archive_branch`, `org.change_system_mode`.

#### 3.10 السجلات المشتركة وغير المسندة تحتاج سياسة صريحة

المرشح الحالي يعرض الصفوف ذات الفرع `NULL` لكل الفروع. يصلح ذلك لقاموس منتجات مشترك، لكنه غير آمن لمستند مالي أو موظف أو حركة تشغيلية غير مسندة.

**الإصلاح:** تصنيف كل مورد إلى:

- `company_shared`: مرجع مشترك مقصود مثل وحدة قياس أو منتج مركزي.
- `branch_owned`: يجب أن يملك فرعًا ولا يظهر لغيره.
- `executive_only`: مستوى الشركة ولا يظهر للأدوار الفرعية.

#### 3.11 الواجهة تعتمد على خريطة الوحدات العامة

إخفاء الزر عبر `canWrite("users")` لا يوضح ما إذا كان المستخدم يستطيع تعيين دور معين أو إدارة هذا الحساب بعينه.

**الإصلاح:** يعيد API قدرات دقيقة (`capabilities`) لكل جلسة، وتظل كل قاعدة مطبقة في الخادم. تعرض الواجهة فقط الأدوار والفروع والأفعال المسموح بها، ورسائل 403 مفهومة عند تغير الصلاحية أثناء الجلسة.

## 4. النموذج المستهدف للأدوار

| الدور | النطاق | الفروع | المستخدمون | بيانات الأعمال | قرارات الملكية |
|---|---|---|---|---|---|
| مالك منصة فيزانو | المنصة | لا يدخلها | فريق المنصة فقط | ممنوعة | الباقات وسياسة المنصة |
| مدير اشتراكات | المنصة | لا يدخلها | لا يدير موظفي الشركات | بيانات تجارية للاشتراك فقط | الفاتورة والتجديد والتعليق |

| المدير العام | الشركة | جميعها | كل مستخدمي الشركة عدا الملكية وفق القرار النهائي | كامل حسب الباقة | لا افتراضيًا |

لا تمنح الباقة صلاحية دور، ولا يمنح وضع المتجر وحدة غير مرخصة، ولا يوسع دور المنصة نطاق بيانات الشركة.

## 5. قرارات مطلوبة قبل تغيير السلوك

1. **الموصى به:** المدير العام يساوي المالك تشغيليًا، وتبقى الملكية والاشتراك وتعيين المالك للمالك فقط.
2. تحديد هل تغيير وضع المتجر يظل للمالك فقط وفق المتطلب السابق، أم يصبح متاحًا للمدير العام بسبب طلب المساواة الجديد.
3. تحديد هل مدير الفرع يستطيع إنشاء مستخدمين داخل فرعه، أم يقتصر على إدارتهم بعد أن ينشئهم المدير العام.
4. تحديد الموارد المشتركة بين الفروع: كتالوج المنتجات والعملاء والموردون والحسابات البنكية والسياسات.

يمكن تنفيذ إصلاحات P0 الآمنة دون انتظار هذه القرارات؛ فهي تمنع وصولًا غير مقصود ولا توسع سلطة أي شخص.

## 6. خطة التنفيذ

### المرحلة 1 — إغلاق الثغرات الحرجة

- تغيير الدور المفقود والأدوار غير المعروفة إلى default deny.
- منع دخول أدوار branch غير المرتبطة بفرع نشط، ومنع حفظ هذا التكوين.
- إضافة `TenantBusinessUserRequired` لكل API أعمال؛ يرفض مستخدم المنصة حتى لو كان superuser عبر API التطبيق.
- إبقاء APIs `/api/platform/*` خلف صلاحيات منصة مستقلة.
- إضافة اختبارات سلبية دائمة لكل حالة.

**القبول:** مستخدم منصة لا يقرأ منتجًا أو راتبًا لشركة، ومستخدم فرعي بلا فرع لا يقرأ شيئًا، ومستخدم بلا دور يحصل على 403.

### المرحلة 2 — حوكمة المستخدمين والأدوار العليا

- إنشاء خدمة مركزية لإسناد الدور تتحقق من actor/target/current role/new role/company/branch.
- إضافة عملية تعيين مالك ثانٍ، ومنع فقد آخر مالك نشط.
- منع تغيير دور الذات أو الشركة أو الفرع عبر PATCH عام إذا كان ذلك يغير مستوى السلطة.
- منح المدير العام عمليات إدارة الشركة المعتمدة.
- منح مدير الفرع إدارة محدودة لمستخدمي فرعه وأدوار أدنى منه.
- تسجيل before/after والفاعل والسبب في ActivityLog.

**القبول:** يستطيع المالك إنشاء مالك ثانٍ؛ لا يستطيع مدير الفرع تعيين مالك أو مدير عام؛ ولا يستطيع أي مستخدم تعديل حساب أعلى منه أو خارج نطاقه.

### المرحلة 3 — توحيد نطاق الفروع

- إنشاء سجل سياسة مركزي لكل model/view/action يحدد نوع النطاق ومسار الفرع.
- تعديل mixin ليطبق العلاقات غير المباشرة ويفشل عند غياب السياسة.
- معالجة المبيعات والمخزون والمشتريات والمرتجعات وCRM وHR والمالية.
- تطبيق السياسة نفسها على الملفات والتصدير والطباعة والبحث والملخصات.
- ترحيل السجلات التشغيلية غير المسندة إلى فرع أو وضعها في قائمة معالجة؛ لا تُنسب تلقائيًا دون دليل.

**القبول:** مدير الفرع لا يرى معرفًا أو مجموعًا أو ملفًا من فرع آخر، حتى بطلب مباشر أو filter أو CSV.

### المرحلة 4 — التقارير والمزامنة ولوحات التحكم

- إضافة `branch_scope` موحد لكل استعلام تقارير وDashboard.
- منع مجاميع الشركة من الظهور لمدير الفرع؛ تعرض مجاميع فرعه فقط.
- تطبيق النطاق على sync push/pull وإعادة الطلبات المؤجلة بعد تغير دور المستخدم أو فرعه.
- اختبار انتقال مستخدم من فرع إلى آخر وإبطال وصوله القديم فورًا.

**القبول:** تتطابق الأرقام في القائمة والتقرير والتصدير والمزامنة لنفس الدور والفرع.

### المرحلة 5 — الصلاحيات الدقيقة والواجهة

- نقل القرارات الحساسة من أسماء الأدوار إلى permission codes مع بقاء الأدوار قوالب جاهزة.
- إرجاع قدرات دقيقة في `/api/auth/me/` أو `/api/rbac/access/`.
- تصفية خيارات الدور والفرع في نموذج المستخدم حسب سلطة الفاعل.
- إضافة رسائل عربية واضحة لحالات نقص الفرع، منع ترقية الدور، وآخر مالك.
- إضافة شاشة للمالكين والمدير العام لعرض هرم الفروع ومسؤوليها.

## 7. مصفوفة اختبارات القبول

تكرر الاختبارات على list/detail/create/update/delete/actions/download/export/sync لكل مورد مناسب:

| السيناريو | النتيجة |
|---|---|
| مالك ينشئ مالكًا ثانيًا داخل شركته | نجاح وسجل تدقيق |
| مالك يحاول تعطيل آخر مالك نشط | رفض ذري |
| مدير عام يقرأ ويدير كل الفروع | نجاح ضمن الشركة فقط |
| مدير عام يطلب شركة أخرى | 404 أو 403 دون كشف الوجود |
| مدير فرع يطلب سجل فرعه | نجاح حسب صلاحية العملية |
| مدير فرع يخمن معرف فرع آخر | 404 دون بيانات |
| مدير فرع يطلب تقريرًا أو CSV | أرقام فرعه فقط |
| مدير فرع بلا فرع | منع دخول/403 واضح |
| مستخدم بلا دور أو دور غير معتمد | 403 لكل وحدات الأعمال |
| مدير فرع يعين مالكًا أو مديرًا عامًا | 403 ولا يتغير الهدف |
| مستخدم منصة يطلب رواتب أو مبيعات شركة | 403 |
| مدير اشتراكات يراجع فاتورة اشتراك | نجاح دون بيانات أعمال الشركة |
| تغيير الدور أثناء وجود جلسة ومزامنة معلقة | يعاد فحص الصلاحية ولا تنفذ عملية قديمة |
| سجل branch-owned بلا فرع | لا يظهر ويُبلغ كخلل بيانات |

## 8. ترتيب الملفات المتوقع تعديله

- `backend/core/rbac.py`: default deny وصلاحيات العمليات.
- `backend/core/scoping.py`: نطاق فرع إلزامي ودعم المسارات غير المباشرة ومنع مستخدم المنصة.
- `backend/accounts/serializers.py` و`views.py`: حوكمة تعيين الأدوار والمالكين.
- `backend/org/store_mode.py` و`views.py`: قرار المالك/المدير العام لوضع التشغيل.
- ViewSets وخدمات التقارير والمزامنة: تعريف نطاق كل مورد.
- `frontend/components/users/UserForm.jsx` وصفحات الإدارة: قدرات دقيقة وخيارات آمنة.
- اختبارات `accounts`, `core`, `integration`, وكل وحدة ذات بيانات فرعية.

## 9. تعريف الاكتمال

تكتمل هذه الخطة عندما لا يعتمد أي قرار أمني على إخفاء الواجهة، ولا يوجد مسار يسمح عند غياب الدور أو الفرع، ولا يستطيع مستخدم منصة قراءة أعمال المشتركين، ويستطيع مالك الشركة إضافة مالك آخر دون إمكان فقد آخر مالك. يرى المدير العام الشركة كلها وفق السياسة المعتمدة، ويرى مدير الفرع فرعه فقط في الشاشة وAPI والتقرير والتصدير والمزامنة، مع اختبارات سلبية تثبت كل حد.
